# Financial Report Question Answering Assistant — Revised Problem Statement

**Student:** Lu Xinze · **Course:** PE6201 End-of-Course Project

**Problem and user.** A junior financial analyst working with an unfamiliar annual report must locate figures across narrative passages and tables, calculate an answer, and verify that the cited material supports it. Keyword search finds terms but does not itself perform or verify multi-figure calculations. This prototype aims to shorten evidence finding while showing both the calculation and its sources. It covers questions about FinQA report excerpts; it does not ingest an entire annual-report PDF, give investment advice, or replace analyst review.

**Why this design.** Rules and keyword search provide a useful low-cost evidence baseline, but they do not handle the variety of FinQA question phrasing and calculations without many task-specific rules. A foundation model can interpret a question and propose evidence-linked arithmetic; retrieval constrains its context to relevant source material. Python performs the arithmetic and checks that cited operands occur in their source passages. An agent is unnecessary for this one-question, one-answer workflow.

**Build and buy.** I build the FinQA preprocessing, MiniLM-plus-NumPy local retrieval, BM25 comparison, answer validation, evaluation harness, and Streamlit interface. I rent one DeepSeek model through OpenRouter because training or hosting a comparable model would add cost and deployment work without serving the project objective. Local vector search is sufficient for a small fixed corpus; a search server is not required.

**Data and privacy.** I use public FinQA development and test examples. Only each example's `pre_text`, `post_text`, and `table` enter the answer pipeline. Gold answers, reasoning programs and marked supporting facts stay outside the retrieval index and are used solely for evaluation. The system processes public research data and stores the API key only in a local ignored configuration file.

**Working slice.** The user selects a report excerpt and enters a question. MiniLM retrieves five core evidence blocks; nearby text and same-table rows are added as separately identifiable context. One model call returns cited operands and bounded arithmetic steps, or abstains. The system validates source quotes and executes the arithmetic in Python before displaying the answer, signed percentage change, citations and evidence.

**Evaluation.** Ten development questions are used to debug the pipeline. Twenty fixed, separate FinQA public test questions compare RAG with a same-model full-context baseline; BM25 measures non-generative evidence retrieval. The primary metric is numerical accuracy against FinQA `exe_ans` under a fixed tolerance and signed-percent convention. Citation support is checked separately by human review; median latency, fraction within 30 seconds, abstention rate, token use and API cost are reported alongside accuracy. The target is 14/20 correct, not a course pass threshold. This small test set has substantial uncertainty. A first formal run was already examined to diagnose failures, so subsequent use of the same 20 questions is reported as iterative comparison rather than an independent test.

**Risk and responsible use.** A cited number can come from the wrong row or year, and a valid arithmetic program can embody the wrong formula. The interface exposes source evidence and intermediate steps so an analyst can inspect them. The system refuses answers with missing evidence or invalid source quotes, and it does not automatically retry or silently substitute values. FinQA itself contains at least one inconsistent textual answer and execution label; the original benchmark score is preserved and such cases are separately documented. Human verification is required before using an answer for financial decisions.
